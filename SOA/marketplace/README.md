# Marketplace Architecture (Arzon)

## 1. Общее описание системы

Arzon — цифровая платформа, обеспечивающая:

* управление пользователями (покупатели и продавцы)
* управление товарным каталогом
* оформление заказов
* обработку платежей
* отправку уведомлений
* персонализированную выдачу ленты товаров

---

## 2. Домены и их ответственность

В системе выделены следующие домены:

### 1. Identity & Access Domain

Ответственность:

* регистрация
* аутентификация
* авторизация
* управление ролями (buyer / seller)

---

### 2. User Domain

Ответственность:

* профиль пользователя
* настройки
* история активности

---

### 3. Catalog Domain

Ответственность:

* создание и редактирование товаров
* управление категориями
* хранение описаний и цен

---

### 4. Order Domain

Ответственность:

* создание заказа
* хранение статусов (created, paid, shipped, cancelled)
* управление жизненным циклом заказа

---

### 5. Payment Domain

Ответственность:

* инициирование платежей
* фиксация результатов
* учёт финансовых операций

---

### 6. Recommendation Domain

Ответственность:

* хранение пользовательских предпочтений
* формирование персонализированной ленты

---

### 7. Notification Domain

Ответственность:

* отправка уведомлений
* реакция на события системы

---

## 3. Распределение доменов по сервисам

Выбранная финальная декомпозиция:

| Сервис                 | Домены         |
| ---------------------- | -------------- |
| Auth Service           | Identity       |
| User Service           | User           |
| Product Service        | Catalog        |
| Order Service          | Order          |
| Payment Service        | Payment        |
| Recommendation Service | Recommendation |
| Notification Service   | Notification   |

Логика разбиения:

* Каждый сервис отвечает за один бизнес-домен.
* Минимизируется когезия между сервисами.
* Упрощается независимое масштабирование.
* Упрощается ownership команд.

---

## 4. Границы владения данными

Принцип: Database per Service.

| Сервис                 | Владение данными              |
| ---------------------- | ----------------------------- |
| Auth Service           | учетные записи, токены        |
| User Service           | профили пользователей         |
| Product Service        | товары, категории             |
| Order Service          | заказы                        |
| Payment Service        | платежные транзакции          |
| Recommendation Service | пользовательские предпочтения |
| Notification Service   | логи уведомлений              |

Общие базы данных отсутствуют.

---

## Взаимодействия сервисов

### Синхронные (REST)

* API Gateway → все сервисы
* Order Service → Payment Service

### Асинхронные (через Message Broker)

* Order Service публикует `order.created`
* Payment Service публикует `payment.completed`
* Notification Service подписывается на события
* Recommendation Service подписывается на события

## 5. Альтернативные варианты декомпозиции

## Вариант A — Монолит

Все домены в одном сервисе:

Marketplace Service:

* Auth
* Users
* Catalog
* Orders
* Payments
* Notifications

Плюсы:

* Простота разработки
* Нет распределённой сложности
* Нет сетевых вызовов

Минусы:

* Невозможно независимое масштабирование
* Сильная связность
* Сложно развивать командно

---

## Вариант B — Микросервисы (выбранный)

Каждый домен — отдельный сервис.

Плюсы:

* Независимое масштабирование
* Изоляция данных
* Чёткие границы ответственности
* Подходит для роста системы

Минусы:

* Сетевая сложность
* Необходимость брокера сообщений
* Более сложный деплой

---

## Вариант C — Гибрид (Domain Cluster)

Объединение связанных доменов:

Service 1: Identity + Users
Service 2: Catalog
Service 3: Orders + Payments
Service 4: Recommendations + Notifications

Плюсы:

* Меньше сетевых вызовов
* Баланс сложности

Минусы:

* Частичное нарушение single-responsibility
* Меньшая гибкость масштабирования

---

## 6. Trade-offs

| Критерий           | Монолит | Микросервисы |
| ------------------ | ------- | ------------ |
| Простота           | Высокая | Низкая       |
| Масштабируемость   | Низкая  | Высокая      |
| Отказоустойчивость | Низкая  | Средняя      |
| Сложность DevOps   | Низкая  | Высокая      |
| Изоляция данных    | Нет     | Да           |

Trade-off:

Мы жертвуем простотой ради:

* масштабируемости
* независимости доменов
* гибкости развития

---

## 7. Обоснование финального выбора

Выбран вариант B — микросервисная архитектура.

Причины:

1. Маркетплейс — система с разными темпами нагрузки:

   * каталог читается часто
   * платежи чувствительны к отказам
   * рекомендации вычислительно тяжёлые

2. Домены естественно изолированы.

3. Требуется персонализация — удобнее реализовать отдельным сервисом.

4. Соответствие принципам SOA.

Учитывая, что бизнес-логика не реализуется, архитектурное разделение демонстрирует зрелый подход к проектированию распределённых систем.
